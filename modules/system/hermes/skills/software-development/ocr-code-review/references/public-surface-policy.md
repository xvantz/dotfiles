# Public surface policy

Как держать чувствительные данные внутри контура, при этом применяя их в работе.

Основной принцип: **знание может быть доступно в момент выполнения, но не должно храниться там, откуда его можно опубликовать.** Публичный репозиторий ссылается на приватные данные, а не содержит их.

## Две зоны

**Зона P (публичная)** — всё, что может уехать наружу:
dotfiles-репозиторий, публичные GitHub/GitLab/Forgejo репозитории, тела PR/MR, сообщения коммитов, логи CI, описания задач в публичных трекерах, любой `git push`.

**Зона V (приватная)** — всё, что живёт только на машине:
`~/.config/ocr-review/` (проектные правила, маппинг репозиториев, список терминов, `provider.env`), `/data/.hermes/`, sops-секреты, приватные репозитории, рабочие задачи.

Правило перехода: P может **ссылаться** на V (`${VAR}`, путь, конфиг), но не **копировать** содержимое V.

## Что можно и что нельзя в зоне P

| Можно | Нельзя |
|---|---|
| Общие практики без привязки к продукту («денежные величины только через Decimal») | Названия продуктов, сервисов, команд, клиентов |
| Имена стека и фреймворков («NestJS + TypeORM») | Имена внутренних модулей, пакетов, эндпоинтов |
| Класс проблемы («внешний вызов без таймаута») | Экземпляр проблемы с деталями («в `SomeService` на платёжном пути нет таймаута у gRPC-вызова») |
| Цифры экономики (время, токены, цена) | Тексты задач, тикеты, бизнес-правила, ставки, объёмы |
| Пути к приватным каталогам (`~/.config/ocr-review`) | Содержимое этих каталогов |
| Схемы и примеры на вымышленных данных (`apps/foo`, `example.com`) | Реальные имена файлов, ветки, SHA с контекстом, ссылки на приватные MR |

Проверка перед публикацией: «можно ли по этому тексту узнать, в какой системе и что именно мы делаем?» Если да — переписать на уровень класса проблемы.

## Четыре слоя защиты

1. **Структурный.** Данные физически лежат вне git-репозиториев, которые публикуются. Проектные правила, маппинг репозиториев и термины — в `~/.config/ocr-review/`. Секреты — в sops, а конфиг ссылается на переменную (`OCR_LLM_TOKEN=${OPENCODE_GO_API_KEY}`), а не содержит значение.
2. **Контрактный.** Этот документ плюс раздел в `SKILL.md`: агент, который правит зону P, обязан пройти чеклист публикации до коммита.
3. **Механический (defense in depth).**
   - `scripts/leakscan --staged` в pre-commit: ловит термин до того, как он попал в коммит.
   - `scripts/leakscan --range origin/master..HEAD` в pre-push: ловит термин в файлах **и в сообщениях коммитов**.
   - CI-джоба на push/PR: серверная проверка, которую нельзя обойти `--no-verify`. Термины приходят из секрета CI, а не из репозитория.
   - `--text` перед созданием PR/MR: тело PR тоже публичная поверхность, и его чаще всего забывают.
4. **Файловер-конфиг.** Если термины не заданы, `leakscan --require-terms` падает с кодом 5. В CI это означает «защита не настроена», а не «всё хорошо».

Термины не только перечисляются вручную, но и **выводятся** (`--derive`) из приватного маппинга: имя проекта, базовое имя репозитория, имя файла проектных правил. Новый проект автоматически попадает под защиту, как только зарегистрирован в `repos.json`.

## Почему термины не печатаются в выводе

Логи CI часто публичны. Сканер, который печатает найденный термин, сам становится каналом утечки. Поэтому вывод — `term[7] (9 симв.)`: достаточно, чтобы найти место, недостаточно, чтобы узнать слово.

## Продвижение из V в P

1. Переписать правило/знание до уровня класса проблемы, без имён и экземпляров.
2. `leakscan --text <файл>` на новый текст.
3. Прочитать глазами: не восстанавливается ли контекст по косвенным признакам (пути, порядок полей, названия ветки).
4. Только после этого — коммит.

Обратный поток (P → V) свободен: из общего правила всегда можно сделать частное.

## Ограничения, честно

- Подстрочный поиск ловит имена, которые ты знаешь и внёс. Пересказ («клиентский сервис выплат») он не поймает. Смысловая утечка остаётся на человеке и на правиле «описывай класс, а не экземпляр».
- Короткие термины (≤4 символов) матчятся только по границам слова, иначе ловятся хэши и base64. Это уменьшает ложные срабатывания и одновременно ослабляет защиту: термин из двух символов внутри другого слова не найдётся.
- `leakscan` смотрит текст, а не историю целиком. После инцидента нужно отдельно чистить историю (squash + force-push) и просить GC на сервере — переписанная история ещё какое-то время лежит в объектах.

## Если утекло

1. Немедленно схлопнуть ветку в один чистый коммит, `git push --force-with-lease`.
2. Проверить серверную ветку: `git grep -i <term> origin/<branch>`.
3. Добавить термин в `~/.config/ocr-review/leak-terms.txt`, если его там не было.
4. Прогнать `leakscan --all-tracked` по всему репозиторию, а не только по ветке.
5. Попросить GC на сервере (`git gc --prune=now` в bare-репо) — без него старые объекты доступны по SHA.
6. Записать в PR/инцидент, что именно утекло и каким механизмом теперь закрыто.
