# Biome Compatibility with NestJS

> **Verified:** 2026-08-02 against biomejs/biome issues #4514, #2038, #10495, discussion #5305, and official docs.

## TL;DR

Two Biome rules/settings interact badly with NestJS experimental decorators. Configure Biome **before** running `--write` on a NestJS codebase, or the auto-fix silently breaks DI at runtime.

## 1. `lint/style/useImportType` BREAKS NestJS DI (critical)

### What happens

Biome rewrites `import { AppService } from "./app.service"` to `import type { AppService }` because the class is only used as a type annotation in the constructor. But NestJS relies on `emitDecoratorMetadata` generating `design:paramtypes` from the **runtime** import. With `import type`, the import is erased and `design:paramtypes` becomes `[Function]` → Nest can't resolve the dependency → crash at startup:

```
Nest can't resolve dependencies of the XController (?). Please make sure that
the argument Function at index [0] is available...
```

### Official Biome position (biomejs.dev/linter/rules/use-import-type)

> "Some frameworks like Angular and NestJS rely on experimental TypeScript decorators... Since Biome doesn't know how a decorator is implemented, it is unable to detect that an import used as a type is also used as a value in the code generated by a decorator... **We haven't found a way to support this pattern yet. We recommend disabling this rule when using such decorators.**"

Issue #4514 (opened Nov 2024, closed "not planned") proposed an `ignoreInjectableClasses` option — never implemented. Discussion #5305 (Mar 2025) — still open, no solution.

### Fix (canonical)

Disable the rule for the NestJS part of the codebase via override (NOT globally if the repo has frontend code):

```json
{
  "overrides": [
    {
      "includes": ["src/backend/**"],
      "linter": {
        "rules": {
          "style": {
            "useImportType": "off"
          }
        }
      }
    }
  ]
}
```

### Community alternative (softer)

`@nedcloarbr/biome-config` uses `useImportType: { level: "info", fix: "none" }` — shows warnings but never auto-fixes. Safer than default, but `off` is more reliable (organizeImports assist action can still reorder).

### Verification

After building, check the compiled JS has the real class in `design:paramtypes`:

```bash
grep "design:paramtypes" dist/src/modules/*/dist/*.js | grep Function
# should NOT show [Function] for injected services
grep "design:paramtypes" dist/src/modules/conversations/conversations.controller.js
# __metadata("design:paramtypes", [centrifuge_service_1.CentrifugeService])  ✅
```

## 2. `javascript.parser.unsafeParameterDecoratorsEnabled` (required)

NestJS uses parameter decorators (`@Body()`, `@Param()`, `@Query()`, `@Req()`). Without this flag Biome reports **parse errors** ("Decorators are not valid here") on every controller. Required in `biome.json`:

```json
{
  "javascript": {
    "parser": {
      "unsafeParameterDecoratorsEnabled": true
    }
  }
}
```

## 3. Recommended: `useExplicitReturnType` (nursery, warn)

Community NestJS configs add this — explicit return types on controllers/services make code self-documenting. Warning level only (it's a nursery rule, still evolving):

```json
{
  "linter": {
    "rules": {
      "nursery": {
        "useExplicitReturnType": "warn"
      }
    }
  }
}
```

## 4. Same trap applies to `@support/shared`-style workspace packages

If a shared package ships **TypeScript sources** (`main: "./src/index.ts"`, `noEmit: true`), prod CJS runtime cannot `require` TS from node_modules (Node 22: `ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`). Fix per pnpm workspace canon:
- `tsconfig.build.json`: `noEmit: false`, `outDir: dist`, `module: nodenext`, `declaration: true`
- package.json: `main`/`types`/`exports` → `dist`, add `"files": ["dist"]`
- Build shared before consumers in Dockerfile: `RUN pnpm --filter @support/shared build`
- `pnpm deploy` then includes `dist` in the pruned tree (verified 2026-08)

## Checklist for a new NestJS + Biome project

- [ ] `unsafeParameterDecoratorsEnabled: true` in biome.json
- [ ] `useImportType` disabled via override for backend paths
- [ ] Run `biome check --write` BEFORE first commit, then verify app boots
- [ ] Guards that hit the DB must validate UUID format first (`z.uuid().safeParse`) or PG returns 500 on bad casts
- [ ] `import type` is only safe for: DTOs used in pipes? NO — DTO classes are ALSO used as runtime metadata by nestjs-zod. Keep value imports for anything referenced in decorators/constructor paramtypes.
